**Мария** боится, что агент «сам отправит» письмо или испортит таблицу. **Алексей** боится обратного: если всё вручную — зачем агент. Datagent держит середину: **агент работает до порога риска**, а дальше решение принимает человек в Board (дублируется уведомлением в Телеграм, если настроено).

![Inbox согласований с несколькими pending](/img/guides/approvals/01-inbox.webp)

*Рис. 1 — очередь «Согласования»: что ждёт решения до рискованного шага.*

## Было и стало

| Было | Стало |
| --- | --- |
| Либо полный запрет tools, либо полная автономия | Tools + **одобрение** на опасное действие |
| «Не знаю, ждёт ли бот моего ответа» | Раздел **Согласования** и уведомления |
| Решения в личке мессенджера | Решение в Board, после чего run продолжается по правилам плагина |

## Что происходит в пятницу с Excel

Ниже — типовой сценарий: агент готовит план изменений, оператор одобряет, система применяет на копии файла.

**Шаг 1. Агент планирует изменения.** Агент «Оформитель таблиц» в задаче с `.xlsx` вызывает `plan_workbook_changes`. Office Plugin помечает шаг как рискованный — требуется [одобрение](../office/excel-pptx).

**Шаг 2. Запрос попадает в очередь.** В разделе **Согласования** появляется карточка: что изменится, идентификатор плана.  
*Результат:* оператор видит запрос до применения, а не после порчи файла.

**Шаг 3. Уведомление в Телеграм (если настроено).** Параллельно администратор мог включить push с кнопками в чат согласований (`approvalsChatId`) — см. [Телеграм](../integrations/telegram).  
*Результат:* решение можно принять с телефона, но источник правды остаётся в Board.

**Шаг 4. Оператор проверяет контекст.** Откройте связанную задачу, посмотрите вложение и план. Одобряйте только если содержание совпадает с ожиданием.  
*Результат:* вы отвечаете за шаг, а не за «зелёную кнопку».

**Шаг 5. Система продолжает run.** После одобрения агент (следующий wakeup или сценарий плагина) может вызвать `apply_workbook_changes`. Новый файл появится вложением на задаче.

**Шаг 6. При отклонении.** Run не выполняет спорный шаг; уточните задачу комментарием и запустите **Wakeup** снова с исправленным intent.

*Рис. 7 — после «Отклонить» запись остаётся в истории с вашей пометкой.*

```mermaid
sequenceDiagram
  participant A as Агент
  participant P as Office Plugin
  participant S as server
  participant M as Мария
  A->>P: plan_workbook_changes
  P->>S: запрос одобрения
  S-->>M: Board и Телеграм
  M->>S: одобрить
  S->>A: продолжение run
  A->>P: apply_workbook_changes
```

Так же устроены одобрения для **BrowserBridge** (`browser_action`) и явный **`request_board_approval`** в manifest пользовательских плагинов.

## Где встроен governance

На совещании Алексей может сказать честно: «Мы не отключили агентов — мы **встроили governance**». Очередь согласований — метрика зрелости (сколько рискованных шагов проходит через людей), а не бюрократия ради галочки.

## Что нельзя делать с одобрениями

- **Не нажимайте «Одобрить», не прочитав задачу.** Вы подтверждаете конкретный шаг tool; ошибка попадёт в файл или канал клиента.
- **Не держите запрос неделями.** Run может ждать решения; дисциплина SLA одобрений — на стороне команды, не «магии» продукта.
- **Не считайте Телеграм единственным местом решения.** Push дублирует Board; журнал и связь с задачей живут в control plane.

## Быстрая победа за 5 минут

Откройте **Согласования**. Если пусто — запомните путь на завтра. Если есть запрос — дочитайте один до конца и примите учебное решение (одобрить или отклонить с комментарием в задаче).
