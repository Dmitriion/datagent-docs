**Алексей** отвечает за операционку и инициативу по агентам. Команда часто просит «одного бота на всё» — без рамок получается хаос: один агент лезет в браузер, другой пишет простыни, третий не видит политику компании. В этой главе вы соберёте **команду ролей** с понятными границами: кто за что отвечает, какие tools доступны и где стоят одобрения.

## Было и стало

| Было | Стало |
| --- | --- |
| Один универсальный промпт на все случаи | Несколько **агентов Datagent** под конкретные сценарии |
| Все tools выданы всем подряд | Только включённые **plugin tools** в manifest каждого агента |
| Непонятно, кто сейчас в работе и где сбой | Статусы **run** и фильтры в списке агентов |

## Как завести трёх агентов за неделю

**Шаг 1. Подготовьте контур с инженером.** Instance поднят, [плагины](../tutorials/build-plugin) установлены (Bitrix24, Телеграм, при необходимости Office Plugin). Без этого агенты не получат нужные tools.  
*Результат:* роли можно привязать к реальным каналам и файлам, а не только к тексту в задаче.

**Шаг 2. Создайте «Аналитик переписки».** Адаптер `gigachat_local` или `yandexgpt_local`, короткий system prompt: «русский язык, структура ответа, без выдуманных цифр». Этого агента оператор будет запускать в задачах с диалогами клиентов.  
*Результат:* ответы по переписке не смешиваются с таблицами и браузером.

![Форма создания нового агента](/img/guides/agents/09-edit-form.webp)

*Рис. 2 — мастер/форма нового агента: имя, адаптер, инструкции.*

**Шаг 3. Второй агент — «Оформитель таблиц».** Те же LLM, в tools только `datagent.excel-workbench:*` после установки [Office Plugin](../office/excel-pptx).  
*Результат:* правки Excel идут через plan → одобрение → apply, а не «на глаз» в чате.

**Шаг 4. Третий — «Внутренний исследователь».** Подключите [BrowserBridge](../browser/setup): tools `datagent.browserbridge:browser_*`, в prompt явное правило: «не отправлять формы и не подтверждать платежи без одобрения». Контракт интеграции — [в разделе «Интеграции»](../integrations/browserbridge).  
*Результат:* веб-исследования изолированы и попадают в очередь согласований при риске.

**Шаг 5. Храните секреты правильно.** `GIGACHAT_*`, `YANDEX_SA_KEY_JSON` — через **secret_ref** компании, не в тексте задачи и не в system prompt.  
*Результат:* оператор не утекает ключами в переписку; инженер ротирует секреты централизованно.

**Шаг 6. Обучите оператора.** Он **не меняет** адаптер и manifest — он **выбирает агента** в задаче и запускает **Wakeup**.  
*Результат:* границы ролей соблюдаются без доступа к настройкам.

**Шаг 7. Раз в неделю смотрите ростер.** В пятницу откройте список агентов: у кого последний run в статусе `failed` — разбор с инженером по журналу, а не «перезагрузите страницу».  
*Результат:* срывы сроков ловятся по факту сбоя run, а не по жалобе клиента.

## Где вы управляете возможностями

Вы задаёте не только текст промпта, но и **границы**: агент не вызовет tool, которого нет в manifest плагина. Нет вымышленных `bitrix24_list_leads` — только сценарии из [Bitrix24](../integrations/bitrix24).

Отдельного поля «поиск по списку агентов» в текущем UI нет — используйте вкладки **Все / Активные / На паузе / Ошибка** и глобальный поиск Board (раздел «Поиск и вход» на [обложке учебника](./)); полноценный поиск по ростеру — в roadmap.

## Что не стоит делать на старте

- **Не выдавайте BrowserBridge и Office всем «на всякий случай».** Очередь согласований вырастет, оператор перестанет успевать — это замедлит, а не ускорит работу.
- **Не пишите секреты в задачу или в system prompt.** Утечка в переписку и журнал run; используйте secret_ref.
- **Не ждите, что агент «сам найдёт» 1С в heartbeat.** Нужен [коннектор](./08-1c-bridge) и MCP в IDE — это другой контур, не tool в run на задаче.

## Быстрая победа за 5 минут

Создайте одного агента с правилом в prompt: «Отвечай только списком из 5 пунктов». Запустите **Wakeup** с карточки — проверьте в журнале run, что граница держится. Так вы за минуту проверяете связку «роль → run → ответ».
