# Рабочие пространства

> **Зачем:** Дать agent **изолированную среду** с кодом, git и сервисами — как отдельную «машину под задачу», а не только чат в браузере.

Два уровня: **project workspace** (шаблон у [проекта](./projects)) и **execution workspace** (живой экземпляр на время run). Оператору CRM обычно не нужно; разработчикам и agent с кодом — нужно.

## Два уровня

| Уровень | Что это | Аналогия |
| --- | --- | --- |
| **Project workspace** | Настройки среды на проекте: драйвер (local / SSH / sandbox), секреты, команды | «Какой ноутбук/сервер у отдела» |
| **Execution workspace** | Живой экземпляр, привязанный к задаче или run | «Временная VM под эту ветку» |

Задача без кода (ответ в Битрикс24, сводка в Excel) **не требует** workspace. Задача «почини тесты в репозитории» — требует.

## Это работает так

1. В [проекте](./projects) настраиваете **workspace** — окружение, политику, при необходимости runtime-сервисы (БД, mock API).
2. Агент берёт задачу с привязкой к проекту; при run создаётся или переиспользуется **execution workspace**.
3. Адаптер работает в этой среде: git, shell, файлы — по политике проекта.
4. По завершении run workspace может **закрыться** или остаться для reuse — зависит от политики и статуса finalize.

:::info Облако и свой сервер
На [app.datagent.ru](https://app.datagent.ru) чаще sandbox и SSH. Полный runbook своего сервера — [on-premise](/docs/cloud/on-premise).
:::

## Project workspace — что настраивают

- **Environment** — откуда выполняется код (локальный агент-хост, SSH, песочница).
- **Секреты** — через [секреты компании](./secrets), не в тексте задачи.
- **Runtime services** — поднять/остановить сервисы (например тестовая БД) из панели проекта.
- **Execution workspace policy** — можно ли переиспользовать среду между run, требования к закрытию.

API: маршруты `projects` и `projectWorkspaces` в `server/src/routes/projects.ts`.

## Execution workspace — жизненный цикл

| Стадия | Смысл |
| --- | --- |
| **Создание** | Run стартует — выделяется workspace под задачу/проект |
| **Работа** | Агент пишет код, гоняет команды; вывод попадает в журнал run |
| **Close readiness** | Проверка: нет ли незакоммиченного мусора, висящих процессов |
| **Finalize / close** | Среда освобождается; артефакты остаются в [каталоге](/docs/artifacts/overview) |

Фильтры списка: `projectId`, `issueId`, `status`, `reuseEligible` — `GET /api/companies/:companyId/execution-workspaces`.

## Безопасность

- Агент **не должен** менять host-level команды workspace без прав — есть отдельные проверки authz.
- Секреты подставляются в runtime, не логируются в переписку задачи.
- Рискованные команды могут упираться в [согласования](./approvals).

## Частые вопросы

**Где кнопка workspace в задаче?**  
Появляется, когда проект с настроенным workspace и задача требует выполнения кода.

**Чем отличается от BrowserBridge?**  
BrowserBridge — браузер на **вашей** станции. Execution workspace — **файлы и shell** в среде проекта.

**Проект без workspace?**  
Нормально. Большинство cloud-сценариев Bitrix24/GigaChat обходятся без него.
